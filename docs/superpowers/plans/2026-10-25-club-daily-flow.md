**Цель:** сделать историю клуба доступной полностью, встречи находить по времени начала, свои редакции и очереди управления понимать без угадывания.

**Архитектура:** существующий Fastify endpoint клубной ленты получает обратно совместимые параметры `limit`, `cursor`, `view`. React использует существующий usePagedCollection и актуальные ACL каждого чтения. Без миграций и новых зависимостей.

**Стек:** действующие React/TypeScript/React Router, Fastify, PostgreSQL, Playwright из package.json.

## Требования и границы

- Читать AGENTS.md, TESTING-STRATEGY.md и scripts/ci/e2e-levels.json. Архитектура, согласия, роли, шифрование и политика закрытой истории сохраняются.
- Лента: курсорная догрузка до конца истории, заметное закрепление, сохранение глубины/прокрутки при возврате с повторным чтением данных. Публикации и встречи остаются в общей ленте.
- Встречи: новая вкладка клуба, «Ближайшие» (предстоящие и текущие open, ends_at > DB time), «Прошедшие» (completed либо истёкшие open), «Отменённые». Ближайшие сортируются starts_at ASC, архив — starts_at DESC. Состояние участия берётся из my_registration; никакого вывода скрытых личностей/общего числа участников из видимого списка.
- Мои публикации: pending/approved/rejected редакции и причина отказа; при ожидающей/отклонённой правке опубликованного поста явно сообщать, что читателям доступна прежняя версия. Непрошедшую редакцию не выдавать за опубликованный пост и не давать ей действия реакций/комментариев. Редактирование и открытие опубликованной версии — отдельные ссылки.
- Управление: группы действий и общая навигация между доступными очередями заявок, публикаций, жалоб. Не выдумывать общие счётчики из ограниченных списков. Вкладка собственных публикаций доступна обычному участнику.
- Новые UI/серверные выдачи не ослабляют текущие ACL. Смена приватности, блок, отзыв членства между страницами применяются к следующему ответу. Курсор не является разрешением.
- Промежуточно — целевые API/E2E, типы и сборка; обязательные FAST → FULL → RELEASE не сокращать.

## API и порядок

`GET /api/v1/clubs/:id/feed?view=feed|upcoming|past|cancelled&limit=20&cursor=...`

- view по умолчанию feed; limit по умолчанию20, диапазон1–50. Ответ `{items,nextCursor}`; существующие DTO и kind post/event сохраняются.
- feed: закреплённый доступный пост первым, затем created_at DESC, id DESC, kind ASC. Закрепление выбирается вне прежней отсечки100.
- event views: starts_at с указанным выше направлением, id DESC/kind ASC для однозначного порядка.
- Новый модуль `server/modules/club-content/listing.ts` экспортирует `clubListing(clubId: string, viewerId: string|null, input: {view: ClubListingView;limit:number;cursor?:string})`. Парсер query остаётся в routes.ts.
- Курсор содержит версию, club/view, непрозрачный HMAC-контекст текущего закрепления для feed и последнюю позицию rank/time/id/kind; строгая проверка, malformed/другой клуб/view/изменённое закрепление →422 invalid_cursor. Время сохраняет микросекунды PostgreSQL, без Date roundtrip.
- Кандидаты читаются SQL-порциями; публикация/встреча повторно проверяется существующим postDTO/canReadEvent. До заполнения страницы+1 видимого элемента продолжать обход; невидимые строки не создают ложного конца истории. Память ограничена порцией и размером страницы. Предварительные SQL-фильтры только сужают набор; окончательные проверки остаются действующими.

## Особое внимание

1. Более100 записей и старое закрепление: все доступны, без дублей при равных датах/микросекундах.
2. Между страницами изменены блокировка/видимость/членство: недоступный материал не выдаётся; cursor не обходит права.
3. Встречи созданы в порядке, обратном времени начала; текущая/истёкшая/отменённая правильно разделены DB-временем.
4. Новая редакция pending/rejected при published: приватный текст и причина только автору; публичная версия остаётся прежней.
5. Мобильная вкладочная навигация, ошибка/повтор догрузки, возврат к странице2 и прокрутке, обычный участник и руководитель.
