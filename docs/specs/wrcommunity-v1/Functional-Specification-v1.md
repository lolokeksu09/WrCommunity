# WrCommunity — Functional Specification v1

**Версия документа:** 1.0-draft · **Дата:** 23 октября 2026 г.  
**Назначение:** сводная функциональная спецификация продукта WrCommunity 1.0 на основе решений раундов 1–9.  
**Статус:** подготовлено к продуктовому и техническому ревью; **это не свидетельство реализации функций**.  
**Репозиторий чтения:** `lolokeksu09/WrCommunity` · проверенная исходная редакция: [`docs/specs/social-core-v1.md`](https://github.com/lolokeksu09/WrCommunity/blob/main/docs/specs/social-core-v1.md) (blob `5e56a88bd506eb81b41bb9b1353142e7e4fa5caf`).  
**Инвариант:** старый проект `wild-rift-community` не используется и не изменяется.

## 0. Нотация и границы утверждения

- **[CORE]** — утверждённый контракт действующего Social Core v1. При конфликте указываем необходимую поправку, не изображаем её внесённой.
- **[USER]** — прямой выбор владельца продукта в раундах 1–8.
- **[DELEGATED]** — оптимальное рабочее решение раунда 9, выбор которого владелец делегировал ассистенту. Оно подлежит обычному ревью, если затрагивает высокорисковые права.
- **[DESIGN]** — рекомендация реализации/интерфейса, не самостоятельное утверждённое пользовательское требование.
- **[OPEN]** — конкретное нерешённое решение, которое нельзя молча зафиксировать при разработке.

Документ описывает желаемое **WrCommunity 1.0**. `Social Core v1` — его базовая подсистема, а не синоним полного релиза: клубы, события и поиск команды должны иметь собственные спецификации с общими проверками приватности и блокировок.

## 1. Продуктовая модель и объём 1.0

**[USER/CORE]** Русскоязычное независимое сообщество игроков Wild Rift, mobile-first веб-сайт. Основная ценность — реальные профили, обсуждения, поиск напарников и сообщества клубов; без симуляции пользователей или активности.

**В первый функционально полный выпуск 1.0:**

1. Регистрация email/пароль, подтверждение почты, восстановление доступа, гостевой просмотр публичного контента.
2. Профили, ручные игровые данные, публичный/скрытый режим, добровольный публичный онлайн-статус, подписки и блокировки.
3. Публикации и комментарии, реакции «Нравится», закладки, темы/категории и @упоминания; общая и подписочная ленты.
4. Компактная сворачиваемая карусель открытий над преимущественно текстовой лентой.
5. Поиск игроков: фильтры, объявления «Ищу команду» (LFG), простые объяснимые рекомендации без ML.
6. Клубы: создание, вступление, управление ролями, публичная/закрытая лента, премодерация публикаций, вложенные обсуждения.
7. Мероприятия: анонсы внутри клубной ленты, участие только членов клуба, лимит мест, управление событием.
8. Центр уведомлений внутри сайта с настройкой событий; базовая модерация, жалобы, журнал действий.

**После начального функционального выпуска:** опросы, затем репосты/цитирование. Не включать без отдельного решения полноформатные чаты, игровые API, турниры с сетками, видео, сложный рекомендательный алгоритм, нативные приложения и внутреннюю монетизацию.

**Последовательность производства** (отдельные проверяемые инкременты, не публичные релизы): I. аккаунты/приватность → II. социальная лента → III. Discovery/LFG → IV. клубы → V. мероприятия → VI. уведомления/пилот/приёмка. Темы и упоминания — при формировании публикаций; опросы и репосты — позднее.

## 2. Учетные записи и профили

### 2.1 Авторизация

- **[CORE]** Email + пароль, обязательное подтверждение email для социальных действий, восстановление доступа через одноразовый ограниченный по времени механизм. Passkeys отложены.
- **[CORE]** Гость читает только разрешённые публичные объекты. Любое создание/вступление/реакция/отклик требует авторизации. После авторизации — возврат в контекст, **без автоматического выполнения первоначального действия**.
- **[CORE]** Профиль при регистрации `hidden`, становится `public` только после ясного выбора пользователя. Уникальный `@handle` отделён от отображаемого имени, в котором допустима кириллица; стабильные ссылки завязаны на immutable ID.

### 2.2 Игровая карточка

- **[USER]** Указывается вручную: сервер, роли, ранг, любимые чемпионы, обычное игровое расписание/время активности, и другие необязательные игровые сведения.
- **[DESIGN]** Каждое игровое поле имеет настройку отображения; статус данных «Указано игроком». Не приписывать верификацию Riot или игровые показатели, которые платформа не проверяла.
- **[USER]** Отдельно: игровое расписание и статус присутствия **на сайте WrCommunity**, не в игре. Показ «В сети» всем посетителям возможен только на публичном профиле, при явном включении; по умолчанию выключен. Скрытый профиль никогда не публикует онлайн-статус.
- **[DESIGN]** Расписание — с часовым поясом и настройкой видимости. Процедуру определения статуса и таймаут отсутствия установить технически без ложной постоянной активности.

### 2.3 Блокировки и приватность

- **[CORE]** Эффективная блокировка A↔B срабатывает, если хотя бы одна сторона заблокировала другую. Запрещены взаимные прямые подписки/реакции/комментарии/адресные ответы/упоминания с уведомлением и будущие LFG-заявки; старые взаимные реакции удаляются, подписки обеих сторон прекращаются.
- **[CORE]** Старые комментарии сохраняются третьим лицам, но скрываются между сторонами блокировки. Публичный гость теоретически может прочитать открытые материалы — блокировка не обещает полной невидимости.
- **[CORE]** `hidden` не раскрывает личный профиль, его публикации, медиа, списки подписок и поисковую карточку. Комментарий скрытого автора под **чужой публичной обычной записью** остаётся публичным с ником без ссылки на профиль.
- **[USER]** Точечные исключения для клубной личности и адресного LFG-отклика описаны ниже; они не переводят основной профиль в `public`.

## 3. Общая главная, публикации и поиск контента

### 3.1 Главная

- **[USER]** В приоритете реальные публикации; компактная **сворачиваемая** карусель открытий над лентой; никаких навязчивых рекомендательных карточек между каждым постом.
- **[CORE]** `Все` — доступные опубликованные записи, по умолчанию по времени; `Подписки` — разрешённые записи авторов подписок. Гость видит только открытое содержимое и явное предложение войти для личных действий.
- **[DESIGN]** Предоставить поиск, сохранение позиции прокрутки, загрузку частями, пустые состояния без фальшивого контента.

### 3.2 Посты

- **[CORE]** Не более 5000 символов текста, 4 изображений по 10 МБ, без видео. Черновики, редактирование, удаление, личные закладки и одна реакция «Нравится» предусмотрены базовым проектом.
- **[USER]** Развитие: сначала темы/теги и @упоминания, затем опросы, позднее репосты/цитаты.
- **[CORE]** Упоминания не обходят блокировки; личные закладки не обходят потерю доступа. Медиа обрабатываются и выдаются с серверной проверкой прав.
- **[DESIGN]** В ленте не использовать тяжёлые нефункциональные обложки для каждого поста; соблюдать спокойный стиль v6 Editorial Social.

## 4. Player Discovery и поиск команды (LFG)

### 4.1 Поиск пользователей

- **[USER]** Все три функции в 1.0: фильтры игроков, объявления о поиске команды, простые рекомендации.
- **[USER]** Сервер и игровая роль — основные критерии. Ранг, расписание, язык, любимые чемпионы — дополнительная сортировка/фильтрация при наличии доступных данных.
- **[DESIGN]** Рекомендация объясняет совпадение («тот же сервер», «нужная роль»); не использует ML и не отображает скрытые профили.

### 4.2 Создание и завершение объявления

- **[USER]** Публичное объявление может создать только владелец публичного профиля. Автор сам выбирает **дату и время окончания** — жёсткий максимальный период не утверждён. В момент истечения новые заявки недопустимы.
- **[USER/DELEGATED]** Автор при создании выбирает политику нерассмотренных заявок: (A) оставить доступными для поздней обработки; (B) автоматически отклонить. Выбор хранится с объявлением.
- **[DESIGN]** Минимальные поля: сервер, искомая роль, описание, срок окончания, политика ожидающих заявок; время сохранять однозначно, показывать в часовом поясе зрителя. Состояния: `draft/open/closed_by_author/expired/deleted`.
- **[DESIGN]** Повторная публикация/продление после истечения — отдельный контролируемый сценарий, не автоматический.

### 4.3 Отклик

1. Гость видит публичное объявление, но для заявки должен войти.
2. Авторизованный пользователь отправляет заявку с коротким сообщением.
3. **[USER]** Скрытый пользователь также может откликнуться, но сначала явно разрешает **только автору объявления** увидеть его ник и текст заявки; полный профиль не раскрывается.
4. Автор принимает либо отклоняет отклик. Проверка блокировки и состояния объявления выполняется при каждой операции.
5. **[DELEGATED]** После принятия допускается добровольный взаимный обмен игровыми контактами; это **не личный чат**. Каждый подтверждает, какие сведения раскрывает.
6. Истёкшее/закрытое объявление не получает новых откликов; оставшиеся обрабатываются выбранной автором политикой.

Состояния заявки: `pending/accepted/rejected/cancelled/auto_rejected`. Запретить дубликаты активных заявок и повторные решения с разными исходами.

## 5. Клубы: создание, вступление и доступ

### 5.1 Создание

- **[USER]** Создатель: подтверждённый email, публичный профиль, удовлетворяет антиспам-требованиям. Максимум **три клуба, которыми пользователь владеет сейчас**; переданные клубы не считаются.
- **[USER]** Обязательны название и описание; остальные поля можно заполнить позже.
- **[USER]** Перед созданием владелец **самостоятельно и явно** выбирает два независимых режима (без предвыбора): `join_mode=open|approval`, `feed_visibility=public|members_only`.
- **[USER]** Даже клуб с закрытой лентой обнаруживается в каталоге по названию/обложке/описанию. Неучастник видит правила и кнопку вступления, **не видит публикаций и состава**.
- **[USER]** После создания пользователь попадает в панель управления клубом. Создатель становится владельцем.
- **[DESIGN]** Сервер атомарно проверяет лимит, права, валидность настроек, антиспам. Повторный запрос не создаёт второго клуба.

### 5.2 Владелец, роли и публичность

- **[USER]** Роли внутри клуба: владелец, администраторы, модераторы и участники.
- **[USER]** **Владелец обязан иметь публичный основной профиль всё время, пока владеет клубом.** Попытка перехода `public→hidden` отклоняется до разрешённого прекращения/передачи владения. Нельзя автоматически удалять клуб.
- **[USER]** Владельцу разрешено менять режим ленты с предупреждением при `members_only→public`, но **новые** публикации становятся доступными более широкой аудитории, а историческая закрытая лента сохраняет прежний режим; изменение не ретроактивно.
- **[DESIGN]** Клубная роль не равна глобальной роли платформы и не даёт полного доступа к скрытым профилям. Назначения ролей, проверки прав, журналы модерации — отдельная подсистема.

### 5.3 Вступление и заявки

- **[USER]** При `open` действующий аккаунт может вступить после серверных проверок; при `approval` создаётся заявка `pending`, членство появляется **только после одобрения**.
- **[USER]** Скрытый заявитель **до** подачи заявки/вступления выбирает для конкретного клуба публичный основной `@handle` либо отдельный клубный псевдоним, клубный аватар и роли; подтверждает строго ограниченное раскрытие этих данных действующим членам клуба.
- **[USER]** До одобрения уполномоченные руководители видят клубный ник/аватар/выбранные роли и только разрешённое содержимое заявки. Ожидающий не входит в список членов.
- **[USER]** При отказе заявитель видит причину **только если** рассматривающий решил её указать. Сам отказ не делает сведения публичными.
- **[USER]** Клубный псевдоним уникален **в пределах конкретного клуба**, смена возможна; история смен доступна уполномоченной модерации. Основной скрытый профиль не открывается по клубной подписи.
- **[USER]** Участники клуба видят согласованные клубные данные скрытых участников. Гости и неучастники видят только публичных членов **публичной** клубной ленты; у закрытой ленты для неучастника состав полностью скрыт.

### 5.4 Выход и отзыв согласия

- **[USER]** Скрытый участник, отзывающий согласие на показ обязательной клубной личности, получает предупреждение и затем автоматически выходит из клуба. Членство и доступ к закрытой ленте прекращаются.
- **[USER]** **Исторические комментарии в клубе** остаются с ником и аватаром, сохранёнными на момент публикации, в пределах исходной аудитории. Перед первым раскрытием и перед выходом нужно явно сообщить, что подписи прежних комментариев не исчезнут.
- **[CORE]** Полное удаление аккаунта отличается от обычного выхода: сохранившиеся комментарии обезличиваются и теряют прежний ник/аватар/ссылку, согласно общим правилам.
- **[DESIGN]** Выход должен сбрасывать доступ к закрытым медиа и закрывать активные регистрации на мероприятия по согласуемой политике; не удалять исторические комментарии автоматически.

## 6. Клубная лента, комментарии, премодерация

### 6.1 Устройство ленты

- **[USER]** Единая лента, где анонсы мероприятий идут **между** обычными публикациями. Одна закреплённая клубная публикация максимум.
- **[USER]** Для всех новых собственных клубных публикаций обязательна **премодерация** руководством. Только пользователь с `public` профилем и действующим клубным членством может создавать клубные посты.
- **[DELEGATED]** Одобрять могут владелец, администраторы и модераторы; администраторы и модераторы не проверяют свои записи. Владелец может одобрить собственную запись при отсутствии другого проверяющего (операционное определение «отсутствия» ещё требует детализации).
- **[DELEGATED]** После редактирования одобренного поста новая версия проходит повторную проверку; до неё видна старая одобренная версия. Все решения фиксируются в аудите.
- **[USER]** Перевод ленты из закрытой в публичную не меняет доступ к старым закрытым постам и комментариям. Считать видимость свойством материала, а не только текущей настройкой клуба.

Статусы поста: `draft/pending_approval/published/rejected/removed`, плюс независимые `visibility_snapshot` и `moderation_state`. Новая редакция хранится отдельно от опубликованной до одобрения.

### 6.2 Комментарии

- **[USER]** Ветки многоуровневые, длинные обсуждения можно свернуть. Система должна сохранять родительскую связь при визуальном ограничении отступов на узком экране; серверная пагинация веток обязательна.
- **[USER]** Публичная клубная публикация: **новые** комментарии создают только действующие участники клуба с публичным основным профилем.
- **[USER]** Закрытая клубная публикация: участники с `public` или `hidden` профилем могут комментировать; скрытые используют клубный ник и аватар.
- **[DELEGATED]** Комментарии публикуются сразу после антиспам-проверок и затем могут модерироваться; общий режим премодерации клубных **публикаций** не распространяется на комментарии.
- **[CORE]** При блокировке стороны не читают комментарии друг друга, включая исторические, и не могут направлять друг другу новые ответы/реакции. Остальные участники читают только в пределах собственной области доступа.
- **[CORE/USER]** При выходе сохраняется историческая клубная подпись, при удалении аккаунта — обезличенное авторство.

## 7. Клубные мероприятия (Events)

- **[USER]** Анонсы событий смешиваются с постами общей клубной ленты. Владелец выбирает, каким ролям разрешено создавать мероприятия.
- **[DELEGATED]** Уполномоченные создатели размещают события без отдельного одобрения; глобальные проверки безопасности действуют.
- **[USER]** Нажать «Участвовать» может **только действующий участник клуба**, даже если анонс публичен.
- **[USER]** Организатор задаёт положительный **лимит мест**; после заполнения новые записи закрываются. Одновременные заявки на последнее место должны разрешаться атомарно без переполнения.
- **[USER]** Организатор мероприятия вправе увидеть клубный ник, клубный аватар и выбранные игровые роли скрытого участника, но не его основной профиль. Публично скрытые участники не отображаются, в том числе через дифференциальные счётчики.
- **[DELEGATED]** Создатель/уполномоченный организатор может редактировать и отменять событие, а зарегистрированные получают внутренние уведомления о существенных изменениях.
- **[DELEGATED]** При отмене участия освобождённое место становится доступным; очередь ожидания не предусмотрена без дополнительного решения.
- **[DESIGN]** Поля: название, описание, дата/время начала, часовой пояс/однозначный момент, положительная вместимость; статус: `draft/registration_open/full/registration_closed/ongoing/completed/cancelled`; отдельные статусы регистрации. Полная турнирная сетка — вне 1.0.
- **[OPEN]** Судьба действующей регистрации после выхода/исключения из клуба; публикация мероприятий скрытыми руководителями; правила переноса времени и окончания регистрации.

## 8. Уведомления и служебная почта

- **[USER]** Социальные уведомления первоначально **только внутри сайта**. По категориям пользователь сам выбирает, что получать. Нет Web Push и социальных email-рассылок в 1.0.
- **[CORE]** Служебные письма подтверждения email и восстановления доступа остаются обязательной инфраструктурой авторизации и не являются социальными уведомлениями.
- **[DESIGN]** Категории: ответы, реакции, @упоминания, решение о клубной заявке, одобрение/отказ клубной публикации, события, отклики LFG, существенные изменения регистрации. Информация уведомления заново проверяется при каждом открытии.
- **[CORE]** Скрытый подписчик не идентифицируется в уведомлении о подписке. Глобальные блокировки не обходятся уведомлениями. Устаревший объект не раскрывается по превью или ссылке.

## 9. Роли, полномочия и модерация

**Роли платформы** (`guest/member/moderator/admin`) независимы от **ролей конкретного клуба** (`owner/administrator/moderator/member`).

| Операция клуба | Owner | Administrator | Moderator | Member |
|---|---|---|---|---|
| Просмотр/изменение базовой приватности клуба | Да | По отдельному делегированию? [OPEN] | Нет | Нет |
| Назначить администратора | Предлагается: да | Нет | Нет | Нет |
| Назначить модератора | Предлагается: да | Предлагается: да | Нет | Нет |
| Рассмотреть заявку на вступление | Да | Предлагается: да | По делегированию? [OPEN] | Нет |
| Одобрить чужую клубную публикацию | Да | Да | Да | Нет |
| Одобрить собственную клубную публикацию | Условно, если нет иного проверяющего | Нет | Нет | Нет |
| Создать мероприятие | Если разрешено конфигурацией ролей | Если разрешено | Если разрешено | Если разрешено |
| Удалить нарушающий правила материал | Да | Предлагается: да | Предлагается: да | Нет, кроме собственного |
| Передать владение | Только владелец [предлагается] | Нет | Нет | Нет |

**[DELEGATED]** Действуют антиспам и последующая модерация комментариев; клубные посты проходят предварительное одобрение, управленческие действия журналируются.

**[CORE]** Жалоба и глобальная модерация не блокируются тем, что нарушитель заблокировал заявителя. Клубные руководители не могут обходить решения платформы или просматривать скрытые персональные данные без специального разрешённого регламента.

## 11. Экранные состояния и ошибки

Все рабочие экраны имеют состояния `loading / ready / empty / validation_error / forbidden_or_not_found / temporary_error`, а операции изменения данных — `idle / submitting / success / conflict / failed`.

- Устаревшая заявка после параллельного одобрения/отзыва согласия → конфликт без неразрешённого членства.
- Смена `public→hidden` владельцем хотя бы одного клуба → отказ до передачи/прекращения владения.
- Три текущих владения → запрет четвёртого клуба даже при одновременных запросах.
- Изменение `members_only→public` → новые материалы публичны, прежний закрытый архив не раскрывается.
- Редактирование одобренного поста → новая версия ожидает проверки; читатели продолжают видеть старую.
- Смена права во время загрузки медиа/комментариев → повторная серверная проверка и немедленное прекращение доступа.
- Заполнение последних мест → победить должен только один запрос, без переполнения.
- Просроченный LFG → запрет новой заявки, применение выбранной политики pending.
- Удаление аккаунта → обезличивание сохраняемых публичных и клубных комментариев; не сохранять доступный идентифицирующий профиль.

## 12. Безопасность, качество и нефункциональные требования

- **[CORE]** Защита от CSRF и недопустимых запросов, аутентификация, безопасные сессии, хеширование паролей, rate limits, server-side ACL и аудит модерации. Не рассчитывать на скрытые кнопки.
- **[CORE]** Для закрытых ресурсов сервер должен не подтверждать существование объекта чужому пользователю там, где требуется (например, 404); кэш, CDN, файлы и уведомления не обходят видимость.
- **[DESIGN]** Touch targets от 44 × 44 CSS px, контраст обычного текста не ниже 4.5:1, понятные фокусные состояния, ввод и навигация клавиатурой, поддержка увеличения текста. Ширины контроля 320/360/390/430 CSS px; отсутствие горизонтального скролла.
- **[DESIGN]** Ленивая загрузка иллюстраций; изображения в современных форматах по возможности; защита от CLS; управление анимацией с учётом reduced motion.
- **[CORE]** Реальные нулевые значения и честные пустые состояния; никакой генерации фальшивых аккаунтов/лайков/событий для украшения экрана.
- **[OPEN]** Юридические условия, возрастные ограничения, политика данных/резервных копий, сроки удаления, изображения и лицензирование игрового контента — до открытого запуска.
