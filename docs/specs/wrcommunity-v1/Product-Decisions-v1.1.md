# WrCommunity — Product Decisions v1.1

**Дата:** 23 октября 2026 г.  
**Статус:** выбранные по делегированию пользователя рабочие решения для архитектурного проекта; требуют итогового ревью перед изменением действующего Social Core v1.  
**Источники:** `Functional-Specification-v1.md`, `Screen-Map-v1.md`, раунды 1–9, действующий `docs/specs/social-core-v1.md` в `lolokeksu09/WrCommunity` (blob `5e56a88bd506eb81b41bb9b1353142e7e4fa5caf`).  
**Граница:** это самостоятельный проект документа; GitHub не менялся. **[CORE]** и **[USER]** важнее предложений ниже; **[DECIDED-BY-DELEGATION]** — не то же, что реализовано или одобрено юридически.

## 1. Неприкосновенные требования

- `hidden` при создании аккаунта; публичность только по осознанному выбору пользователя. Отдельные клубные и адресные LFG-раскрытия не открывают основной профиль.
- Гость читает разрешённый публичный контент; любые социальные действия требуют подтверждённой учётной записи. Возврат из входа не выполняет действие автоматически.
- Эффективная блокировка двусторонняя: прекращение подписок, удаление взаимных реакций, отказ от прямых взаимодействий, скрытие исторических комментариев сторон друг от друга при сохранении их для остальных правомочных читателей.
- Удаление аккаунта обезличивает сохранённые комментарии; выход из клуба не равен удалению аккаунта.
- Пост: до 5000 символов, максимум 4 изображения по 10 МБ, без видео. Опросы и репосты не входят в начальную полнофункциональную поставку.
- Создать клуб может только публичный подтверждённый профиль с антиспам-допуском; не более 3 клубов в текущем владении. Владелец обязан оставаться публичным.
- В клубе 4 роли: владелец, администратор, модератор, участник; каждую клубную запись одобряет руководство; одна закреплённая; мероприятия в общей ленте; организатор назначает лимит мест; участвуют только члены клуба.
- Скрытый член закрытого клуба может комментировать под согласованной клубной личностью; новые комментарии в публичной клубной ленте и собственные клубные посты — только с публичным профилем.
- LFG: создание — только публичным профилем, дата окончания по выбору автора без искусственного максимума, короткий отклик, скрытый откликающийся раскрывает ник только адресату по согласию; после принятия возможен двусторонний opt-in на игровые контакты, без чата.
- Онлайн означает присутствие на сайте, не в игре; публичный показ всем доступен только публичным профилям и лишь после отдельного включения (по умолчанию выключен). Уведомления социального типа — только внутри сайта, с настройками.

## 2. Решения по 15 ранее открытым вопросам

| Код | Делегированное решение | Причина и инвариант |
|---|---|---|
| OD-01 | Имя клуба 3–60 Unicode grapheme clusters; описание 10–1000; клубный псевдоним 3–32; обложка до 10 МиБ; клубный аватар до 5 МиБ. Название клуба не обязано быть глобально уникальным, URL всегда на immutable UUID. | Меньше ложных коллизий, ограниченная нагрузка; Unicode NFC, whitespace normalization, защищённые служебные имена. Глобальный `@handle` остаётся уникальным по правилам Social Core. |
| OD-02 | Создание: подтверждённый email, активный публичный профиль, не более трёх текущих владений, не чаще 1 клуба за 24 часа и 3 за 30 дней на аккаунт; отдельные адаптивные лимиты по риску. | Снижение спама без непрозрачного «рейтинга доверия». Частотные пороги — стартовая настраиваемая политика, не раскрывать внутренний риск-скоринг. |
| OD-03 | Рассмотрение вступления и исключение: владелец и администраторы. Модераторы управляют постами, комментариями и жалобами; исключение участника только при отдельном выданном разрешении. | Минимальные полномочия, отзыв прав проверяется при каждом действии. |
| OD-04 | Передача владения: владелец инициирует, будущий владелец явно принимает; будущий владелец публичен, имеет подтверждённый email, проходит антиспам-проверку и не превышает трёх текущих владений. Операция атомарна. Архивация клуба не удаляет владельца и продолжает учитываться в лимите. Удаление только отдельной подтверждённой процедурой. | Запрет бесхозных клубов и обхода лимита. |
| OD-05 | Комментарий при публикации получает защищённую историческую подпись (клубный псевдоним/аватар). После обычного выхода/отзыва клубного согласия подпись сохраняется ТОЛЬКО в прежнем разрешённом обсуждении; публичного профиля или активного членства не появляется. После удаления аккаунта подпись обезличивается и медиа-ссылки отзываются. | Совместимость с прямым решением пользователя раунда 6 и §8 Social Core. Предупреждение об исторической подписи до вступления. |
| OD-06 | Скрытый администратор/модератор с разрешением может оформить мероприятие **от имени клуба**, а не как личную публикацию: публичная карточка указывает клуб как организатора, без персональной идентификации. Информация о реальном создателе — в закрытом журнале управленческих действий по полномочиям. | Событие — объект клуба, а не обход запрета `hidden` создавать собственные публичные посты. |
| OD-07 | Выход/исключение из клуба автоматически отменяет будущие активные регистрации участника на клубные мероприятия; освобождаются места, внутреннее служебное событие получает организатор без раскрытия закрытых данных сверх разрешённого; история аудируется. | В мероприятиях участвуют только действующие члены клуба. Операция атомарна. |
| OD-08 | Мероприятие имеет `starts_at`, `ends_at`, `registration_closes_at`, вместимость. При существенном изменении (время/место в рамках платформы/отмена) создаётся внутреннее уведомление зарегистрированным; записываться можно только до `registration_closes_at` и до начала. Отмена сохраняет историю, новые действия запрещены. | Предсказуемое участие, единая модель времени. |
| OD-09 | После обычного отказа в заявке на вступление повторная подача разрешена через 48 часов; после исключения — через 7 дней, если не действует отдельный запрет повторного вступления/санкция. Результат и причина видны только заявителю и уполномоченным. | Защита от повторного спама; интервалы — конфигурируемая политика платформы. |
| OD-10 | Администратор и модератор не могут одобрять свои посты. Владелец может одобрить свой только при отсутствии другого **активного, доступного и незаинтересованного** проверяющего (администратора/модератора с правом проверки). Событие требует причины и audit trail. | Сохранение согласованного исключения без обхода независимой проверки; обычные собственные посты владельца иначе ждут другого проверяющего. |
| OD-11 | Публичные счётчики клуба и мероприятия отражают **только видимые этому зрителю личности**; не показывать полный/видимый счётчики вместе. Для события статус «Мест нет» допустим без общего числового occupancy. Организатор видит точную вместимость по своей полномочной области. | Не допускать вывода количества скрытых участников через арифметическую разницу. |
| OD-12 | Клубные имена уникальны в пределах клуба по нормализованной форме; служебные слова и имитация полномочий запрещены. Смена имени требует проверки, новая подпись действует только для будущих комментариев, история смен видна уполномоченным модераторам. Старые имена сохраняются зарезервированными на период существования связанных исторических подписей. | Не допускать подмены исторического автора и споров из-за старых имён. |
| OD-13 | **Не фиксируется без правовой оценки:** минимальный возраст, региональные условия, lawful basis, сроки очистки личных данных, обращения, журналы, сроки резервных копий и процедуры удаления. До пилота без посторонних пользователей требуется отдельный юридический/комплаенс-gate. | Точный закон и срок нельзя честно «выбрать» без юрисдикции и оценки данных. Архитектура должна позволять конфигурируемую retention-политику и исполнение запросов. |
| OD-14 | **Не фиксируется без проверки прав:** изображения, имена игровых персонажей, логотипы Riot, пользовательские вложения, лицензирование бренд-материалов. Первая реализация использует собственные оформительские материалы и нейтральные иконки. Перед публичным запуском — rights review, правила UGC и takedown. | Исключение заведомых лицензионных нарушений. |
| OD-15 | Принятие LFG-заявки открывает возможность добровольно указать игровой контакт и явно раскрыть его **конкретному принятому собеседнику**. Каждый участник отдельно подтверждает действие; по умолчанию не раскрывается ничего. Отзыв отменяет дальнейший показ, но не удаляет уже сохранённые получателем копии — сообщить об ограничении. | Нет автоматической выдачи email, телефона, адреса или полного hidden-профиля. |

## 3. Ещё семь важных инженерных решений

1. **Изменение режима ленты:** при `members_only → public` старый архив остаётся закрытым, новые посты получают разрешённую публичную область после премодерации; при `public → members_only` закрыть ранее опубликованные записи для будущих серверных чтений и инвалидировать публичные кэши. Внешние копии задним числом не исчезают — предупредить.
2. **Согласие клубной личности:** привязано к `(user_id, club_id, version_of_policy)`; ясно показывает аудиторию, набор полей и правило сохранения исторических подписей. Повторное одобрение заявки при отзыве согласия не создаёт active membership.
3. **Постановка комментариев:** клубные комментарии появляются без премодерации, но с лимитами, защитой от abuse, жалобами и постмодерацией; посты — с обязательной премодерацией. Исторические комментарии сторон блокировки фильтруются на сервере, а не только CSS.
4. **Реакции и упоминания:** проверка блокировки и видимости на любом уровне вложенной ветки; приватный комментарий нельзя цитировать в публичной подсказке или уведомлении.
5. **Редактирование клубного поста:** видна последняя одобренная редакция; новая сохраняется в `pending_review` до решения. При скрытии профиля автора ранее одобренная собственная запись становится закрытой. Запрещено мутировать уже одобренный контент «на месте».
6. **Удаление:** обычный выход сохраняет исторический клубный ник/аватар в ACL обсуждения, удаление аккаунта обезличивает; удаление клубной записи исключает её из API и медиа; юридически необходимая запись аудита не отображается публично.
7. **Уведомления:** выключение пользовательской категории ограничивает необязательные социальные уведомления, но важные служебные сигналы безопасности и подтверждение email остаются обязательными; внутреннее содержимое проверяется при открытии, а не хранит закрытый текст в push/email.

## 4. Полномочия клуба — базовый профиль

| Полномочие | Owner | Admin | Moderator | Member |
|---|---|---|---|---|
| Настройки клуба / приватность ленты | Да | Нет | Нет | Нет |
| Передача владения | Инициировать | Нет | Нет | Нет |
| Назначение admin | Да | Нет | Нет | Нет |
| Назначение moderator | Да | Да | Нет | Нет |
| Вступления по заявке | Да | Да | Нет | Нет |
| Исключение пользователя | Да | Да (кроме равной/высшей роли) | Только отдельное разрешение, не выше роли | Нет |
| Одобрение чужой публикации | Да | Да | Да | Нет |
| Одобрение своей публикации | Только OD-10 | Нет | Нет | Нет |
| Модерация комментариев / жалоб | Да | Да | Да | Жаловаться |
| Создание мероприятий | Если право роли включено | Если право роли включено | Если право роли включено | Если право роли включено |
| Отмена мероприятия | Создатель или owner | Создатель или уполномоченный admin | Создатель в пределах прав | Создатель в пределах прав |
| Просмотр скрытых личных профилей | Нет | Нет | Нет | Нет |

Клубные полномочия НЕ заменяют глобальные `guest/member/moderator/admin`; администратор клуба не равен администратору всей платформы. Все операции с изменением прав пишутся в журнал; автор/владелец объекта не получает неограниченных исключений.

## 5. Статус проектных решений и последствия

- **Прямые решения пользователя:** сохраняются без пересмотра. Численные лимиты OD-01/OD-02, интервалы OD-09, механизм OD-10 и UX OD-15 — самостоятельный delegated design, а не «ранее утверждённые пользователем значения».
- **Блокеры открытого запуска:** OD-13 и OD-14, политика abuse/appeal, процедура жалоб и удаления, эксплуатационная готовность. Достоверность юридической политики и лицензий не гарантирована этим документом.
- **Не реализовано:** сервер, база данных, интеграции, работающие экраны, уведомления и полномочия. Это проект продуктового контракта для последующего ревью и разработки.
