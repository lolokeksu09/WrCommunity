# Управление VDS через GitHub Actions

Текущий пилот: `https://139.100.205.135`, Ubuntu 24.04, 2 CPU, 2 ГБ RAM и 2 ГБ swap. Compose-проект — `wrcommunity-local`; исходная конфигурация находится в `/opt/WrCommunity`. Письма пока принимает закрытый Mailpit; внешний SMTP остаётся отдельной задачей.

## Доступ и границы

GitHub Actions подключается по SSH под отдельным пользователем `wrc-deploy`. Ключ разрешает две команды: `status` и `deploy <SHA> <CI_RUN_ID>`. Переадресация портов, PTY и интерактивная оболочка запрещены. Пользователь не входит в группу Docker. Root-контроллер установлен отдельно, принадлежит root и запускается через ограниченное правило sudo.

Контроллер принимает только текущий HEAD `lolokeksu09/WrCommunity:main`. Он дополнительно запрашивает GitHub API и проверяет, что в указанном push-запуске `.github/workflows/ci.yml` успешно завершились оба задания `integration` и `docker-smoke`. PR, fork, другая ветка, неверный SHA, пропущенные/неуспешные проверки и устаревшая версия отклоняются. GitHub Actions с правом изменения доверенного `main` получает возможность обновлять код приложения на VDS; доступ к репозиторию следует предоставлять соответственно.

Приватный ключ создаётся на VDS. `gh secret set` передаёт его через stdin в зашифрованные GitHub Actions Secrets. Публичный ключ SSH-сервера берётся непосредственно с VDS и фиксируется в known_hosts; проверка ключа обязательна. Ключи, `.env`, SMTP-пароли и содержимое базы не передаются в чат или публичные логи CI.

## Однократное подключение оператором

После слияния этого изменения оператор выполняет в существующей root SSH-сессии на VDS:

```bash
cd /opt/WrCommunity &&
git pull --ff-only origin main &&
bash scripts/deployment/install-access.sh
```

Скрипт установит необходимые Ubuntu-пакеты и запустит авторизацию GitHub CLI через браузер. Оператор сам подтверждает вход в GitHub; код авторизации не нужно отправлять в чат. Требуются административные права на этот репозиторий для записи Secrets. Временная локальная конфигурация авторизации CLI удаляется после завершения скрипта.

Установка создаёт ограниченную SSH-учётную запись, root-контроллер и отдельное правило sudo. Настройки существующего входа root и SSH daemon не меняются. Перед включением проверяется локальное SSH-подключение с тем же ключом и pinned host key. При повторном запуске существующий ключ сохраняется. Неожиданные права/группы существующей учётной записи приводят к остановке установки.

Secrets: `WRC_DEPLOY_KEY`, `WRC_DEPLOY_KNOWN_HOSTS`.

Variables: `WRC_DEPLOY_HOST`, `WRC_PUBLIC_ORIGIN`, `WRC_DEPLOY_ENABLED`. Последняя включается в конце успешной установки. До этого merge и CI сами по себе не развёртывают приложение.

Установщик затем запрашивает read-only задание статуса в GitHub Actions. Его успешный результат подтверждает доступ из GitHub; локальная SSH-проверка сама по себе этого не доказывает.

## Обновление

После успешных проверок push в `main` задание `deploy` отправляет точный SHA контроллеру. Статус-задание `vds-status` возвращает только состояние/health/OOM контейнеров, версию релиза, свободное место и публичную readiness-проверку. Задание можно отдельно повторить через GitHub Actions API, чтобы проверить VDS без повторного деплоя. В интерфейсе GitHub доступен также ручной запуск Application CI с операцией `status` на `main`.

Контроллер последовательно выполняет:

1. Проверку источника, CI, текущего `main` и свободного места; блокировку конкурентного деплоя.
2. Создание отдельного каталога релиза и образа `wrcommunity:<SHA>`. Сборка происходит до копирования `.env` в каталог; неуспешная сборка оставляет текущий сайт работающим.
3. Копирование существующих локальных настроек без генерации новых секретов. Эффективная Compose-конфигурация проверяется до остановки: проект, volumes PostgreSQL/media, пути монтирования, закрытая сеть и отсутствие публичных портов БД/API должны сохраняться. Полученный JSON с секретами не выводится в логи.
4. Остановку API и worker, согласованную локальную копию PostgreSQL и media, проверку читаемости dump/архива и контрольных сумм. Неудача до миграций запускает прежние API/worker снова.
5. Миграции и запуск нового образа, проверку HTTPS с обязательной проверкой сертификата, readiness и собранной страницы. После успеха сохраняется идентификатор активного релиза.
6. Браузерную проверку публичной главной и формы входа на 390 и 1440 px; скриншоты сохраняются в артефакте `deployed-public-site`. Учётные записи, публикации и другие записи на работающем сайте проверка не создаёт.

Обновление сопровождается коротким перерывом на согласованную копию и миграции. Если ошибка возникла после начала миграций, контроллер останавливает API/worker и требует восстановления оператором: автоматического отката схемы или запуска потенциально несовместимого старого кода нет. Образы, копии и неудачные релизы сохраняются; автоматического удаления данных и `docker prune` нет. При недостатке места следующий деплой отклоняется.

SQL-миграции требуют проверки до слияния в `main`. Разрушительные изменения схемы или существующих production-данных требуют отдельного явного разрешения владельца. Настройка автоматического деплоя не отменяет это правило; текущий патч не добавляет миграций.

## Файлы и восстановление

Рабочая конфигурация: `/opt/WrCommunity/.env`, `compose.vds.yml`, `compose.ip.yml`, `Caddyfile.ip`. Эти host-specific файлы исключены из Git. Релизы: `/opt/wrcommunity-releases/<SHA>`. Состояние и закрытые журналы сборки/запуска: `/var/lib/wrcommunity-deploy`. Копии базы, медиа и настроек: `/root/wrcommunity-deploy-backups` с доступом только root. Приватный deploy-ключ: `/root/.config/wrcommunity-deploy`.

Копии локальные, не зашифрованы отдельно и не заменяют внешнее зашифрованное хранение или проверенное восстановление production-данных. Предыдущий образ сохраняется, но откат образа после изменения схемы требует проверки совместимости. Автоматическое восстановление БД намеренно отсутствует.

Для отзыва доступа root может переместить `/var/lib/wrc-deploy/.ssh/authorized_keys` в резервный файл вне `.ssh`; это немедленно запретит новые подключения этим ключом. Переменная `WRC_DEPLOY_ENABLED=false` дополнительно отключает автоматические задания. Действующий SSH-сеанс обновления следует сначала завершить или дождаться окончания. Изменение кода контроллера требует повторного запуска установщика оператором: приложение не перезаписывает собственный привилегированный gateway.

## Проверки и ограничения

Unit-тесты контроллера проверяют разбор команд, shell injection, происхождение CI, отказ при неуспешных проверках и восстановление после частичной остановки до миграций. Docker smoke дополнительно проверяет настоящую локальную Compose-схему: публикацию Caddy/Mailpit и отсутствие внешних портов API/БД.

Отдельный workflow `Live public site check` проверяет действующий публичный сайт без SSH-ключа и без обхода TLS. Ошибка сертификата останавливает его до открытия браузера. Наличие файлов workflow не доказывает установленный SSH-доступ: установка, первая проверка статуса из GitHub и первый деплой должны быть подтверждены реальными запусками.
