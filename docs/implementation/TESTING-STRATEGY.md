# WrCommunity — регламент выбора и запуска тестов

**Статус:** действующее руководство для разработчиков и AI-агентов. **Дата:** 24 октября 2026 года.  
**Область:** репозиторий `lolokeksu09/WrCommunity`, только ветка `main` и рабочие PR.  
**Приоритет:** утверждённые требования `docs/specs/` и [AGENTS.md](../../AGENTS.md), затем этот регламент. Этот документ **не изменяет** конфигурацию CI, политику слияния или правила деплоя.

## 1. Основное правило: минимум локально, полный контроль перед релизом

Для каждого изменения действуют три этапа:

1. **FAST (Draft PR / в процессе разработки):** автоматические `fast` (typecheck, сборка, секреты, CI-policy) и выбранные агентом **целевые** L1–L3 тесты по рискам. Для багфикса сначала RED (новый тест падает по правильной причине), затем GREEN. Не запускать весь E2E-набор вручную после каждого промежуточного изменения; перед переводом PR в Ready убедиться, что выбранные поведенческие проверки действительно выполнены.
2. **FULL (Ready PR):** последний SHA ветки должен пройти `integration`, `docker-smoke` и `quality-gate` со статусом именно **success**. Перевод из Draft в Ready запускает FULL заново. Не сливать при pending, skipped, failure или cancelled у любой FULL job. Число тестов изменяется вместе с проектом.
3. **RELEASE (после merge в `main`):** ещё раз дождаться проверок для **точного merge SHA**, затем `deploy` и `vds-status`. Проверить публичный HTTPS и соответствие активной ревизии. При выключенном `WRC_DEPLOY_ENABLED` или пропуске job не заявлять, что деплой состоялся.

**Реализация CI:** [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) автоматически выбирает этап по **состоянию PR**, а не по догадкам о затронутых файлах. В **Draft PR** запускается job `fast` (проверка регламента CI, секретов, TypeScript и сборки), а `api-tests`/`browser-tests`/`integration`/`docker-smoke` не запускаются. После перевода в **Ready for review**, повторного открытия или нового коммита в готовый PR параллельно запускаются `api-tests`, `browser-tests` и `docker-smoke`, после чего `integration` требует успеха обоих тестовых заданий. Постоянно исполняемый для PR job `quality-gate` проверяет результаты соответствующего этапа и завершается ошибкой при неверном/неуспешном наборе. При push в `main` выполняются прежние FULL-проверки, после которых возможны `deploy` и `vds-status`. Важное условие: проверка `quality-gate` должна быть назначена обязательной настройками защиты ветки GitHub; до подтверждения этих настроек агенты **вручную** запрещают merge без успешных `integration`, `docker-smoke` и `quality-gate` на актуальном SHA.

## 2. Правило классификации изменений

Перед тестированием просмотреть `git diff --name-only` и реальный diff относительно `main`, импортируемые компоненты, изменённые маршруты, API, схемы и контракты. Выбирать **объединение** проверок для всех затронутых областей. Не считать изменение «только CSS», если оно меняет доступность кнопки, адаптивную навигацию или видимость защищённых данных.

| Изменение / условие | FAST: что проверять при разработке | Дополнительная проверка по риску |
|---|---|---|
| Только `*.md`, описания и ссылки | Проверить точность команд, существование целевых файлов/путей, ссылки, отсутствие противоречий с `AGENTS.md` и CI; проверить diff | Нет нужды вручную запускать UI/E2E для текста. **Автоматические checks PR пока всё равно обязательны** |
| CSS, размеры, иконки, responsive | `npm run build:web`; целевой Playwright на затронутом экране | Состояния 360/390/430/1440 px, overflow, keyboard focus, safe areas, reduced motion, доступные имена; при изменении логики — `npm run typecheck` |
| React, роутинг, формы, публикации, комментарии, изображения | `npm run typecheck`, `npm run build:web`, целевой E2E изменённого сценария | Гость/авторизованный, desktop/mobile, загрузка/ошибка/повтор, сохранение данных/фокуса |
| Авторизация, сессии, приватность, блокировки, санкции, модерация, медиа ACL | `npm run typecheck`, затронутые `tests/*.test.ts`, соответствующий E2E с несколькими аккаунтами | Обязательны позитивные **и отрицательные** проверки доступа: скрытый/публичный, владелец/посторонний, заблокирован, отсутствует право; не ограничиваться CSS |
| Fastify API, серверная валидация, реакции, клубы, LFG, события | `npm run typecheck`, `npm run build:server`, затронутые API-тесты | Корректность контрактов, доступов, конфликтов и повторных запросов; E2E, если поведение видно в UI |
| PostgreSQL, SQL, миграции, запросы, курсоры | `npm run migrate` на **отдельной тестовой БД**, целевые API-тесты | Повторная миграция, целостность/конкурентность, `npm run backup:verify` в изолированной среде; не запускать разрушительные миграции на production |
| Worker, очереди, email, уведомления | Целевые worker/API-тесты; E2E с запущенным worker + тестовым Mailpit | Доставка/повторы/ошибки, сохранение видимости и отсутствие уведомлений, раскрывающих скрытую личность |
| Docker, Compose, Caddy, деплой, SSH, CI/workflows, секреты | Проверка затронутого конфига, `npm run check:secrets`, соответствующие скриптовые/деплой-тесты | Обязательные `docker-smoke` и проверки восстановления/публичного HTTPS в CI. Не отключать защиту SHA, TLS, host key, бэкапы |
| Изменение самих тестов, зависимостей или общей тестовой инфраструктуры | Перезапуск затронутых тестов, проверка конфигурации, typecheck/build по области | Для фреймворка или общей фикстуры — расширить охват до всех зависимых сценариев |

Если изменение затрагивает несколько строк матрицы, **применять все релевантные правила**, а не выбирать самую дешёвую строку. Изменения безопасности, миграций и деплоя считаются повышенным риском независимо от размера diff.

## 3. Проверенные команды репозитория

Работать в корне WrCommunity, в среде с Node.js 24.x / npm 11 и установленными зависимостями (`npm ci`).

```bash
npm run check:secrets
npm run typecheck
npm run build:web
npm run build:server
npm run build
npm test
```

**Целевой API-тест** (существуют `tests/social.test.ts`, `tests/security.test.ts`, `tests/worker.test.ts`, `tests/auth.test.ts` и другие):

```bash
node --import tsx --test --test-concurrency=1 tests/social.test.ts
```

**Целевой браузерный сценарий** (существуют `tests/e2e/notification-quick-read.spec.ts`, `comment-thread-usability.spec.ts`, `home-feed-ux.spec.ts` и др.):

```bash
npx playwright test tests/e2e/notification-quick-read.spec.ts --config scripts/playwright.config.ts --project=mobile-chromium
npx playwright test tests/e2e/comment-thread-usability.spec.ts --config scripts/playwright.config.ts --project=desktop-chromium
```

Без `--project` тест запускается для **обоих** проектов: `desktop-chromium` и `mobile-chromium`. [`scripts/playwright.config.ts`](../../scripts/playwright.config.ts) задаёт **1 worker локально**, **2 по умолчанию в CI** и **3 в полном CI** через `WRC_E2E_WORKERS=3`, при этом `fullyParallel: false` сохраняет последовательность сценариев внутри каждого spec-файла. В CI сохранён один повтор при неуспехе. Дальнейшее увеличение параллелизма требует отдельной проверки на общие данные PostgreSQL и Mailpit.

**Перед запуском E2E** требуются рабочие test PostgreSQL и применённые миграции, собранный web/server, корректные тестовые переменные окружения. Playwright по умолчанию поднимает `npm start` (если `E2E_BASE_URL` не задан); сценарии email/уведомлений/очередей дополнительно требуют `npm run start:worker` и Mailpit. Просто выполнить указанные две команды на чистой машине **недостаточно** — использовать окружение, воспроизводящее `browser-tests` job из CI. Не подключать E2E к production-БД.

**Полный браузерный набор** (только по правилам FULL):

```bash
npm run test:e2e
```

**Проверка миграций / восстановления** — только в отдельной disposable-среде c корректными переменными и PostgreSQL:

```bash
npm run migrate
npm run backup:verify
```

**Docker smoke:** `sh scripts/docker-smoke.sh`; также CI выполняет `bash scripts/local-compose-smoke.sh` и тесты `scripts/deployment/test_*.py`. Требуются Docker/Compose и доступ к Docker daemon. Не выдавать статическую проверку `compose config` за выполненный smoke.

## 4. Рабочий алгоритм агента

1. **Определить риски:** перечислить изменённые файлы, общеиспользуемые зависимости, границы данных, затронутых пользователей и приватность. Указать целевые тесты и причины исключения других.
2. **RED:** при баге/новом поведении создать минимальный регрессионный тест и доказать его падение **по причине отсутствующего поведения**, а не из-за неготовой БД, невалидной фикстуры, тайм-аута или опечатки. Вариант проверки допускается через локальный целевой запуск до push в PR. Не нужна целая батарея E2E ради одного RED.
3. **GREEN:** внести минимальное изменение, выполнить целевой тест, затем typecheck/build и остальные FAST-проверки из матрицы. При ошибках выяснять причину, исправлять и повторять нужные проверки.
4. **Зафиксировать и отправить:** коммиты в короткоживущей ветке, документация в том же PR. Предпочитать осмысленные завершённые серии правок вместо частых push только ради запуска GitHub Actions.
5. **FULL:** перевести Draft PR в **Ready for review** только после проверки изменённого поведения; затем подтвердить `integration`, `docker-smoke` и `quality-gate` у **актуального head SHA PR**. При добавлении коммитов в Ready PR полный набор запускается снова. Не объявлять PR проверенным по старому успешному run. Перед merge ещё раз проверить SHA, результат всех трёх jobs и защиту ветки.
6. **RELEASE:** после merge проверить отдельный CI на `main`, `deploy` и `vds-status`, read-only проверку сайта и активную ревизию. Не создавать тестовые аккаунты/контент на production. При ошибке/пропуске указать реальный статус, не скрывать проблему.
7. **Отчёт:** перечислить команду или job, ветку/SHA, результат (pass/fail/skipped/not run), причину пропуска, ссылки на PR/CI и статус сайта. Если проверка не выполнялась — написать «не запускалась», а не «успешно».

## 5. Что разрешено не запускать вручную

- При чистой документации — локальный PostgreSQL, API-интеграцию, браузер и Docker; достаточно верификации документов/diff. **Но** существующий автоматический PR CI останется полным.
- При чистом визуальном CSS без изменения контрактов — ручные миграции/backup, весь набор серверных API и весь набор E2E; проверить целевую страницу/ширины и сборку.
- При локальном исправлении одного React-сценария — остальные E2E-файлы до финального CI, если нет общих изменений в навигации/сессии/фикстурах.
- Повторный запуск **того же** целевого теста на том же SHA, с теми же входными условиями и подтверждённым успехом — не нужен без новой причины. Применимо к ручным проверкам, **не** отменяет обязательные jobs GitHub.

## 6. Что нельзя пропускать или подменять

- Проверки прав доступа/скрытых данных, когда затронуты API, разрешения, состояния профиля, клубов, блокировки, медиа или уведомления.
- Проверки БД и восстановления при миграциях/изменениях хранения; контроль deployment при изменении Docker, CI или SSH.
- Обязательные `integration`, `docker-smoke`, `quality-gate` со статусом **success на последнем Ready PR SHA**, полные повторные проверки на merge SHA перед автоматическим deploy, `deploy`/`vds-status` и внешний HTTPS при публикации. Пропущенная job со статусом `skipped` **не** равна успешной FULL-проверке.
- Запреты: `test.skip`/`test.only` для обхода поломки, удаление неуспешного теста ради зелёного CI, отключение TLS/SSH host key, обход PR, изменение workflow ради «зелёного» статуса, исполнение тестов на production с мутациями, публикация приватных логов и секретов.

Если нет доступа к нужной инфраструктуре, агент **останавливает утверждение об успехе**, фиксирует причину и использует доступный GitHub CI. Исключения из обязательных проверок требуют явного решения владельца проекта и отдельного изменения утверждённых release gate; данная инструкция такого разрешения не даёт.

## 7. Примеры выбора

- **Поправить отступ карточки публикации:** `npm run build:web` + E2E конкретной страницы на мобильной ширине. API/backup вручную не нужны. Финальный PR CI полный.
- **Исправить «Прочитано» в уведомлениях:** RED/GREEN `tests/e2e/notification-quick-read.spec.ts` на соответствующем проекте, typecheck/build. При серверных изменениях + `tests/worker.test.ts` и отрицательные проверки приватности. Финальный PR CI полный.
- **Исправить вложенные комментарии:** `tests/e2e/comment-thread-usability.spec.ts`, typecheck/build; при изменении API также `tests/social.test.ts`/`tests/security.test.ts`. Финальный PR CI полный.
- **Изменить таблицу/миграцию:** изолированная PostgreSQL, миграция и повторное применение, целевые API, проверка сохранности данных и `backup:verify`. Финальный PR CI полный.
- **Изменить CI/деплой:** проверить scripts/конфиги, Docker/скрипты контроллера, полные jobs и защищённый VDS-цикл; не ослаблять условия обязательного прохождения.

## 8. Автоматические этапы и ограничения

| GitHub событие | Выполняемые проверки | Условие перехода |
|---|---|---|
| Новый Draft PR / новый commit в Draft | `fast` + `quality-gate`, без полного набора | Агент вручную запускает нужные целевые сценарии и переводит PR в Ready только после завершения изменения |
| `ready_for_review`, `opened` как Ready, `reopened` как Ready, `synchronize` как Ready | `integration` + `docker-smoke` + `quality-gate` | Только `success` всех FULL jobs на актуальном SHA разрешает merge |
| `converted_to_draft` | Снова `fast` + `quality-gate` | Draft не допускается к слиянию |
| `push` в `main` | FULL (`integration` + `docker-smoke`), затем возможны `deploy` и `vds-status` | Нужна подтверждённая публичная проверка и активный SHA |

**Технические гарантии:** `quality-gate` исполняется через `if: always()`, проверяет состояния зависимых jobs и завершается с кодом 1 при несоответствии этапа. Действующий деплой по-прежнему имеет `needs: [integration, docker-smoke]` и привязку к `github.sha`; проверки SSH, TLS, приватности и бэкапов не меняются. Набор инвариантов закреплён в `scripts/ci/test_ci_stages.py` (Python stdlib) и исполняется в FAST и FULL.

**Ограничение доступа:** только администратор репозитория может подтвердить и включить обязательный check `quality-gate` и запрет обхода в Branch protection / Rulesets. GitHub считает условно пропущенные jobs успешными для некоторых настроек required checks. Поэтому без такой настройки **нельзя** обещать технически гарантированную блокировку merge; агенты обязаны соблюдать ручной fail-closed контроль FULL. Для ускорения FULL используется ограниченный параллелизм Playwright — **три worker в полном CI, два по умолчанию в CI без явной настройки, один локально**; `fullyParallel: false` запрещает параллельный запуск отдельных тестов внутри файла. Это не две независимые БД: новые глобальные фикстуры или сценарии, использующие общие данные, требуют пересмотра настройки и отдельного прогона.

**Почему не пять отдельных CI:** L1–L3 — категории выбранных агентом коротких функциональных проверок, L4 — FULL перед merge, L5 — проверка реального релиза. Это одна система с тремя запускаемыми этапами, без пяти независимо обслуживаемых пайплайнов.

## 9. Исполняемая классификация L1–L5

Сценарии Playwright классифицированы в **[реестре `scripts/ci/e2e-levels.json`](../../scripts/ci/e2e-levels.json)**. Реестр хранит имя реально существующего теста, его уровень `L2` или `L3`, и функциональную область. Он **не** меняет текст сценария и не дублирует его шаги. Контракт `scripts/ci/test_e2e_classification.py` отказывает в FAST, если новый тест не получил одну однозначную классификацию, был удалён из реестра или осталась несуществующая запись.

| Уровень | Исполняемый набор | Этап |
|---|---|---|
| **L1 — Instant** | `npm run test:l1`: быстрые проверки структуры и инвариантов CI, классификации, команд без запуска PostgreSQL/браузера | Автоматически в Draft FAST и готовом FULL |
| **L2 — Quick** | `npm run test:l2`: короткие E2E сценарии из реестра, при необходимости по конкретной области | Агент выборочно при работе над функцией |
| **L3 — Functional** | `npm run test:l3`: многошаговые сценарии и проверки сохранения состояния | Агент до перевода PR в Ready |
| **L4 — Integration** | Параллельные `api-tests` (все API, миграции, backup, проверки кода) и `browser-tests` (все E2E, миграции, worker), затем агрегатор `integration`; одновременно `docker-smoke` и затем `quality-gate` | Обязательный FULL готового PR и `main` |
| **L5 — Release** | `deploy` с read-only проверкой реального HTTPS и `vds-status` с активным SHA, доступностью контейнеров и БД | Только после полного L4 на `main` |

### Запуск выборочных сценариев

Из корня проекта с установленными зависимостями, **в изолированном E2E-окружении** из §3:

```bash
npm run test:l1
npm run test:l2 -- feed --project=mobile-chromium
npm run test:l2 -- comments --project=desktop-chromium
npm run test:l3 -- auth
npm run test:l3 -- notifications --project=mobile-chromium
```

Без выбора области запускаются все сценарии указанного уровня для desktop и mobile. Поддерживаются `--project=mobile-chromium`, `--project=desktop-chromium` и `--list`. Увидеть выборку, **не** запуская браузер, можно так:

```bash
npm run test:l2 -- feed --dry-run
npm run test:l3 -- auth --dry-run
npm run test:l2 -- --list
```

L2/L3 вызывают реальный Playwright без заглушек: локально один worker, по умолчанию в CI два file-level worker, в полной GitHub Actions при `WRC_E2E_WORKERS=3` — три; используется прежний тестовый сервер/Worker, если конкретные сценарии их требуют. **`--dry-run` и `--list` не являются пройденными функциональными тестами.** Если для уровня и области нет сценариев, селектор завершается ненулевым статусом: нельзя выдавать пустой прогон за успех.

Текущие области: `auth`, `social`, `clubs`, `lfg`, `moderation`, `forms`, `navigation`, `feed`, `comments`, `media`, `notifications`, `editor`. Реестр покрывает **20 объявлений тестов** в 7 E2E-файлах; параметризованный тест адаптивности порождает несколько вариантов по ширине экрана.

### Обязательное правило агента

Перед целевым тестом классифицировать изменённые файлы и влияние общих зависимостей по матрице §2, затем выбрать **объединение** L2/L3 по всем реально затронутым областям. При изменении поведения добавить регрессию и зарегистрировать её в реестре **в том же PR**. Не выбирать автоматически только самый короткий тест и не игнорировать безопасность ради скорости: auth/ACL/приватность при необходимости требуют целевых серверных тестов уже на FAST, а полный L4 обязателен перед merge. FAST проверяет обнаружение доступных групп через `--list`, но целевые браузерные L2/L3 исполняет агент в подготовленном окружении. Наличие классификации не заменяет `npm run test:e2e` в FULL.

### Ограничения

В L1 нет визуальных браузерных утверждений: мгновенный запуск достигнут за счёт статических контрактов, не имитации UI. Присваивание L2/L3 отражает **глубину сценария**, а не гарантированную продолжительность. В полном CI сейчас три worker на уровне spec-файлов; по умолчанию при ручном запуске с `CI=true` без дополнительной переменной — два. Покрытие FULL не сокращено; при признаках гонок вернуть `WRC_E2E_WORKERS: '2'`, а при подтверждённой проблеме также на двух worker — к одному либо обеспечить полноценную изоляцию тестовой БД.

## 10. Выбор L2/L3 по изменённым файлам — Smart Affected Plan

Команда `npm run test:affected` строит **рекомендации**, а не имитацию прохождения тестов. Селектор `scripts/ci/plan-affected.mjs` читает существующий реестр `scripts/ci/e2e-levels.json` и объединяет необходимые функциональные области для *всех* изменённых файлов.

```bash
# Проверка конкретной UI-правки без запуска браузера:
npm run test:affected -- --files web/src/notifications.tsx

# Несколько файлов: объединяются области media + notifications:
npm run test:affected -- --files web/src/post-gallery.tsx web/src/notifications.tsx

# Полный diff между базовым коммитом и текущим HEAD (потребуется доступный base SHA):
npm run test:affected -- --base=<40-значный-SHA>

# Машинно-читаемая форма для агентов и других скриптов:
npm run test:affected -- --json --files web/src/social.tsx
```

При `--base` используется безопасный вызов `git diff --name-only -z` с полным набором изменений, включая удалённые файлы. Если базовый SHA недоступен, diff не читается или список пуст при явном запросе, команда **завершается с ошибкой**, а не объявляет нулевое покрытие успешным. Для локального запуска можно передать точные файлы через `--files`.

На стадии **Draft FAST** workflow получает `github.event.pull_request.base.sha`, загружает эту ревизию и выводит отчёт по **всему diff PR**, а не только последнему коммиту. Это важно при серии промежуточных изменений. При этом FAST не поднимает тестовую PostgreSQL/Worker и не запускает Playwright в браузере: выполнение рекомендованных L2/L3 по-прежнему ответственность агента в изолированном окружении. `quality-gate` не считает рекомендации успешными E2E-тестами.

### Приоритеты классификации

| Изменения | Решение селектора |
|---|---|
| Только документация (`docs/**`, `*.md`, `AGENTS.md`) | `documentation-only`: L2/L3 не предлагаются; L1 и остальные проверки текущего CI сохраняются |
| Изолированные компоненты (`web/src/notifications.tsx`, `post-gallery.tsx` и др.) | `targeted`: конкретная область, например `notifications` или `media` |
| Известные страницы, обслуживающие несколько сценариев (`web/src/social.tsx`) | Объединение всех связанных областей без исключения остальных |
| Общие файлы (`styles.css`, `ui.tsx`, `main.tsx`, общие E2E-фикстуры, конфигурации CI) | `expanded`: все области реестра |
| Сервер, права доступа, безопасность, БД, неизвестные пути | Консервативное `expanded`: все области; для серверных/защищённых изменений обязательны целевые API и **отрицательные** проверки доступа |
| Новый E2E-файл без записи в реестре | `expanded` плюс ошибка проверки реестра на уровне L1, пока новый сценарий не классифицирован |

Вывод содержит режим `targeted/expanded/documentation-only`, список затронутых файлов, области, количество зарегистрированных сценариев L2/L3 и команды `npm run test:l2/l3 -- <area>`. Он не учитывает неявные зависимости приложения автоматически: для новых модулей консервативно выбираются все области, а для затронутого общего кода или ACL агент обязан расширить проверку по регламенту независимо от вывода скрипта.

**Обязательные ограничения:** планирование изменённых областей работает только для оптимизации промежуточной разработки. Оно **никогда не фильтрует** `npm run test:e2e`, `integration`, `docker-smoke` и проверки VDS в FULL/RELEASE. Не использовать `--files` с заведомо неполным списком PR для обхода тестов. Изменённые маршруты авторизации, модерации, приватности и БД требуют ручной проверки серверных рисков даже при зелёном L1.

## 11. Выполнение затронутых L2/L3 — Affected Execute

Режим `--execute` **запускает** проверки, отобранные по полному diff или по указанным файлам. Это отдельное **явное действие** агента в подготовленном изолированном окружении E2E (тестовая PostgreSQL, применённые миграции, собранные web/server, Worker и Mailpit при необходимости). **Draft FAST на GitHub по-прежнему только строит план, не запускает тяжёлые E2E автоматически.**

```bash
# Посмотреть будущие команды, не выполняя тестов:
npm run test:affected -- --execute --dry-run --files web/src/notifications.tsx web/src/post-gallery.tsx

# Запустить L2/L3 затронутых областей одним Playwright-прогоном:
npm run test:affected -- --execute --files web/src/notifications.tsx web/src/post-gallery.tsx

# Только мобильный браузер (при UI-итерации):
npm run test:affected -- --execute --project=mobile-chromium --files web/src/social.tsx

# Реальный diff от известного SHA:
npm run test:affected -- --execute --base=<полный-40-символьный-SHA>
```

**Правила выполнения:**

- `targeted`: все совпадающие L2 и L3 сценарии собираются в **один Playwright запуск** с `--grep`, без повторных запусков одних и тех же тестов при нескольких затронутых областях.
- `expanded` (общие/неизвестные пути): выполняется **один полный** `npm run test:e2e`, а не десятки независимых групп.
- `securitySensitive` (сервер, авторизация, ACL): перед полным E2E также запускается `npm test` на изолированной PostgreSQL; его отказ блокирует браузерный запуск. Дополнительно агент проверяет отрицательные сценарии доступа и специфические риски — общий API-прогон не доказывает корректность нового механизма автоматически.
- `documentation-only`: явно выводится, что E2E не выбран. Нельзя представлять это как успешный браузерный прогон.
- `--dry-run` показывает команды **без выполнения** и допускается только вместе с `--execute`. Вывод не является доказательством прохождения тестов. `--json` сохраняет существующий режим плана и несовместим с `--execute`.
- Ошибки тестов, отсутствие инфраструктуры и нераспознанные аргументы **не скрываются**: команда завершается ненулевым кодом. Все дочерние команды вызываются без shell-интерполяции.
- `--project=desktop-chromium|mobile-chromium` используется только по явному запросу; без него включены оба проекта Playwright.
- Для полного PR оставаться обязательными `integration`, `docker-smoke` и `quality-gate`; для релиза — `deploy` и `vds-status` на проверенном SHA. Нельзя заменять их успехом локального `--execute`.

**Зачем это ускоряет работу:** до этого `test:affected` выдавал отдельные команды по области, которые при выполнении по очереди могли заново проверять один и тот же сценарий и неоднократно запускать Playwright. `--execute` объединяет выборку и исполняет её один раз. Это не меняет фактическую длительность обязательного FULL CI и не гарантирует фиксированное ускорение без замеров.

## 12. Ограниченный параллелизм полного браузерного набора

Исходная оценка: [успешный CI на main до оптимизации](https://github.com/lolokeksu09/WrCommunity/actions/runs/40088684971) выполнял **42 успешных браузерных сценария примерно за 3,5 минуты** при `workers: 1` (без изменения тестов). Исходная оптимизация увеличила число worker с 1 до 2 в CI; текущая конфигурация имеет параметр `WRC_E2E_WORKERS` с дефолтами 2 в CI и 1 локально, а полный workflow выставляет 3. Это параллельно исполняет **разные spec-файлы**, а тесты внутри одного файла остаются последовательными (`fullyParallel: false`). Это уменьшает суммарное время ожидания, не убирая проверки и не меняя `retries` или FULL/RELEASE gate.

**Ограничения:** все spec-файлы CI по-прежнему используют одну тестовую PostgreSQL, Mailpit и Worker. Текущие сценарии создают индивидуальные учётные записи и используют адреса/ID для выборки. При добавлении новых тестов нельзя опираться на глобальное количество публикаций или общую очередь модерации; новые фикстуры должны быть изолированы. При обнаружении гонки сначала вернуть `WRC_E2E_WORKERS: '2'` в полном CI и расследовать причину; если гонка воспроизводится на двух worker — снизить до одного, пока изоляция не исправлена. Не помечать тесты skip. Два worker были исходной точкой сравнения; три worker включены только после FULL-замеров PR #17.

**Как оценивать производительность:** сравнивать длительность строки `N passed (...)` в job `browser-tests` (в исторических прогонах — `integration`) на том же наборе браузерных тестов, дополнительно учитывать число failures/retries и итоговый статус `docker-smoke`, `deploy` и `vds-status`. Не выдавать сокращение Playwright-времени за такое же сокращение общего CI/CD, поскольку подготовка окружения, Docker и деплой занимают отдельное время.

Не заменять такие проверки увеличением порогов, безусловными повторами или `skip`; устранение зависимости от порядка общих данных важнее дальнейшего параллелизма. Перед merge обязателен новый успешный FULL на исправленном SHA.

## 13. Параллельный FULL: API и браузер (эксперимент PR #21)

**Схема:** на Ready PR и push в `main` запускаются **одновременно**, на разных GitHub runners: `api-tests` (проверка секретов, TypeScript, сборка, L1, миграции, все API-тесты, backup verify), `browser-tests` (сборка, миграции, Chromium, worker и полный Playwright для desktop/mobile с `WRC_E2E_WORKERS=3`) и `docker-smoke`. У `api-tests` и `browser-tests` **отдельные** PostgreSQL и Mailpit; данные, миграции и служебный процесс браузерного worker не разделяются между jobs. Внутри `browser-tests` прежняя изоляция на уровне spec-файлов не меняется.

**Агрегатор:** job `integration` с `if: always()` и `needs: [api-tests, browser-tests]` явно требует `success` **обоих** заданий; при `failure`, `cancelled` или `skipped` возвращает ненулевой код. `quality-gate` на готовом PR требует успешных `integration` и `docker-smoke`, а `deploy` на `main` по-прежнему зависит от этих двух jobs и проверяет конкретный SHA. Draft запускает только FAST. Новая проверка инвариантов — `scripts/ci/test_parallel_full.py` (L1), в дополнение к `test_ci_stages.py`.

**Сравнение:** базовый `integration` до изменения выполнялся за **215–228 с** в трёх успешных FULL-прогонах (API 47–53 с; Chromium install 20–26 с; браузерный этап 104–106 с). После разделения сравнивать время **от старта FULL до успешного агрегатора `integration`** и отдельно wall-clock Ready PR до `quality-gate`. Сохранить 56 API-тестов, 42 браузерных passed и 4 штатных skipped. Накладные расходы независимых runner учитывать отдельно; один успешный запуск — только предварительный замер, а не гарантия производительности.

**Первый FULL-замер:** [PR #21, Ready run 40106205046](https://github.com/lolokeksu09/WrCommunity/actions/runs/40106205046) — `api-tests` **88 с** (56/56 API), `browser-tests` **176 с** (42 passed, 4 штатных skipped, 3 workers), `docker-smoke` **56 с**, `integration` и `quality-gate` — success. Критический путь от запуска независимых jobs (`15:16:21 UTC`) до завершения `integration` (`15:19:24 UTC`) составил **183 с**, против 215–228 с у монолитного `integration` в трёх предыдущих успешных прогонах: экономия примерно **32–45 с (15–20%)**. При сравнении общей длительности workflow учитывать отдельно очереди GitHub Actions и запуск `quality-gate`. Это первый подтверждённый FULL-замер; для окончательного SHA и повторной проверки надёжности требуется новый FULL после внесения записи в регламент.

**Решение и откат:** эксперимент допускается к `main` только при успешном FULL на **последнем SHA**, неизменном покрытии, отсутствии необъяснимых retries и подтверждённом снижении критического пути. При регрессии закрыть PR без слияния или вернуть исходный единый `integration` отдельным проверенным PR. Не удалять `docker-smoke`, `quality-gate`, release checks, бэкапы или защиту по SHA.

## 14. Эксперимент: Chromium headless shell для FULL и RELEASE (PR #22)
