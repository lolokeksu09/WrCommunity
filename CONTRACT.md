# Implementation contracts (internal)

Root owns server/db/migrations/001_initial.sql, server/db/index.ts, server/app.ts, server/index.ts, server/types.ts, server/lib.ts.

All routes /api/v1. Register modules as `export async function registerX(app: FastifyInstance): Promise<void>` from server/modules/<module>/routes.ts. Import helper `query<T>(text, values?, tx?) -> Promise<T[]>`, `one<T>(...) -> Promise<T|undefined>`, `execute(...) -> Promise<void>`, `transaction(fn: (tx: PoolClient)=>Promise<T>)` from ../../db/index.js. T unconstrained. `lockUsers(tx, ids: string[])` obtains canonical ordered user locks. `lockPair(tx,a,b)` advisory pair lock; all follow/block/reaction/comment/LFG direct operations must use it.

`request.viewer: Viewer|null` set by global auth hook. Viewer fields: id,email,verified:boolean,handle,display_name,visibility:'public'|'hidden',platform_role:'member'|'moderator'|'admin',status:'active'|'suspended'|'deleted'. `request.sessionId: string|null`. Import types from ../../types.js. `requireUser(request, verified=true): Viewer` from ../../lib.js. Unverified can edit profile/settings but no social mutation. `fail(status,code,message): never` throws structured HttpError. `idParam(request,name='id'):string` validates UUID; `parse(schema,value)` zod parse with 422 error. `notify(tx,recipient,eventType,objectType,objectId,actorId?)` inserts outbox notification. These helpers are root-owned.

Policy/social agent owns ../../modules/policy/service.ts: `blocked(a,b,tx?)`, `canReadPost(viewerId:string|null,postId:string,tx?) -> Promise<boolean>`, `canReadProfile(viewerId,profileId,tx?)`, `postDTO(postId,viewerId,tx?) -> Promise<unknown>` optional postDTO may live social/service. Public statuses checked every read. Club agent implement own member/role helpers clubs/service.ts; expose `membership(userId,clubId,tx?)`, `canReadClubContent(userId:string|null,clubId,audience,tx?)` and `canManageClub(userId,clubId,roles?,tx?)`. Every agent can directly use shared SQL contract below, no dependencies on helper implementation timing.

All SQL table/column names and constraints defined in 001_initial.sql; no agent edits it. Agents can propose additive migrations numbered auth 010, social 020, clubs 030, lfg/events 040. All response lists `{items:[...]}`; detail is object itself; mutations return object or `{ok:true}`. Date ISO strings. Auth GET /auth/session -> `{user:Viewer|null,csrfToken:string}`. Cookie session, CSRF global. Client sends X-CSRF-Token on writes, global strict origin. Register/login/reset public still require CSRF fetched session. Root mounts routes and static SPA and swagger. API errors `{error:{code,message,requestId}}`.

Frontend reads API via central client (web owner), do not create mocks/localStorage data. Routes aim at Screen Map but consolidate states. Server modules document implemented endpoints in docs/implementation/API-<module>.md so frontend can wire exact routes. Each agent owns tests/<module>.test.ts using node:test, Fastify inject and real PostgreSQL; helper tests/helpers.ts root will supply `app`, `resetDatabase`, `createUser({visibility?,verified?,platform_role?}) -> {id,cookie,csrf,viewer}` and `request(method,url,user?,payload?)`. Test helpers can create users directly in test DB; no test endpoints in production.

Use Node 24 node:test with tsx (`node --import tsx --test --test-concurrency=1 tests/*.test.ts`). Tests reset/truncate between suites? Prefer unique test data, no global destructive reset during tests. For isolated test function use unique UUIDs/handles. createUser helper uses auth endpoint and DB email verification then session login.
