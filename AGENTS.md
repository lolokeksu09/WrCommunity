# Правила работы — Project Workflow Standard 1.4-rc3 (адаптация)

Прочитай [PROJECT.md](PROJECT.md), [TESTING-LEVELS.md](TESTING-LEVELS.md) и действующие файлы перед изменениями. Сверяй ветку, HEAD, diff и реальные проверки.

- Источник требований — решение владельца и [план](docs/PLAN.md). Не добавляй функции «для красоты»: сначала работающий импорт, просмотр, затем точечное редактирование.
- Различай факты, гипотезы, результаты проверок и запланированное. Не утверждай, что APK протестирован на Android, если проведена только сборка.
- Не восстанавливай код/контент Wild Rift Community. Не изменяй VDS/данные/секреты/доступы без отдельного явного разрешения.
- При простом изменении используй Light, при зависимых этапах — Full с одним реестром REQ-ID. Режим документации **не снижает** требования к проверкам по риску.
- Перед исправлением ошибки воспроизведи сбой, затем выполни целевую проверку. Если не удалось — документируй ограничение.
- Не подменяй визуальную проверку UI успешной компиляцией. Сохраняй отчёт о реально проверенной версии и окружении.
- Для рискованных действий объясняй воздействие до выполнения. Публикация/merge требует действующего разрешения; PR и успешный CI не означают релиз.
- Изолируй работу в ветке, делай минимальные изменения. Секреты и личные модели не коммить в публичный репозиторий.
- Сохраняй доказательства exact SHA, точный CI run и статус; skipped не равен passed.
- Если проверка недоступна — честно назови недоступную проверку и остаточный риск.

Детальные исходные нормативные формулировки и шаблоны находятся в предоставленном владельцем архиве `Project-Workflow-Standard-v1.4-rc3.zip`. Этот файл не заменяет полную редакцию стандарта при спорных случаях.
