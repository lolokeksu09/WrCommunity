# AGENTS.md — обязательные правила работы с WrCommunity

Этот файл действует для всего репозитория и всех AI-агентов, работающих с проектом.

## Источник истины

- Единственный репозиторий: `https://github.com/lolokeksu09/WrCommunity`. Целевая ветка: `main`.
- Утверждённые пользовательские решения и `docs/specs/social-core-v1.md` имеют приоритет; также учитывай `docs/specs/wrcommunity-v1/`. Предложение (PROPOSAL) не является утверждённым требованием.
- Сохраняй текущую архитектуру (React + Fastify + PostgreSQL + worker + Docker/Caddy), действующие API-контракты, названия файлов и правила приватности. Не подменяй реальные серверные данные демо-содержимым.
- Старый `wild-rift-community` не является репозиторием этого проекта; `prototypes/home/v6/index.html` сохраняется как исходный прототип.

## ОБЯЗАТЕЛЬНО: коммиты, GitHub и документация

**Ни один законченный патч не считается доставленным, пока изменения не сохранены в GitHub и не обновлена соответствующая документация.**

1. Перед работой прочитай актуальный `main`, относящиеся к задаче исходники и документацию; не предполагай, что локальная копия актуальна.
2. Каждый логический патч оформляй реальным Git-коммитом и отправляй в `lolokeksu09/WrCommunity`; не оставляй готовые изменения только локально, в чате или на VDS. При работе через GitHub API создание/изменение файла в ветке уже создаёт удалённый коммит.
3. Работай через короткоживущую ветку и PR в `main` для изменений кода и существенных настроек. Документация должна быть обновлена **в этом же PR до слияния**. Если задача большая, коммить и отправляй каждый завершённый этап, не накапливай несохранённую работу.
4. При каждом функциональном патче обновляй относящиеся к изменению документы: `README.md`, `docs/implementation/*.md`, описание API/операций/ограничений, а при необходимости `CONTRIBUTING.md`. Не изменяй утверждённые спецификации задним числом без решения владельца.
5. Перед слиянием проверь фактический результат: подходящие тесты + обязательные проверки `Application CI` (`integration`, `docker-smoke`). Для исправлений поведения добавляй регрессионный тест. Не выдавай созданный тест за пройденный.
   - **Как выбирать тесты:** перед началом работ прочитай [`docs/implementation/TESTING-STRATEGY.md`](docs/implementation/TESTING-STRATEGY.md). Создавай Draft PR для промежуточного `fast` CI и запускай целевые L1–L3 тесты по рискам. После завершения патча переведи PR в Ready for review: на последнем SHA обязательно дождись **success** у `integration`, `docker-smoke` и `quality-gate`. Не сливай при `skipped`, `pending` или отсутствии любой FULL-проверки. Затем RELEASE на `main` с проверкой фактического SHA VDS. **Без подтверждённой защиты ветки администратором этот контроль обязателен вручную**, даже если GitHub показывает Merge.
6. Сливай в `main` только проверенный PR. Обычный push в `main` запускает автоматический деплой через `.github/workflows/ci.yml`, **если** включён `WRC_DEPLOY_ENABLED`. После слияния проверь отдельный CI, `deploy`, `vds-status` и проверку публичного сайта. Если любой шаг не выполнен, сообщи об этом, не утверждай, что релиз опубликован.
7. В каждом итоговом отчёте указывай URL PR (если есть), точный SHA коммита в `main`, перечень правок, какие документы обновлены, результаты CI и реальный статус VDS/сайта. Не заменяй доказательства предположениями.

## Безопасность production

- Деплой возможен только через установленный ограниченный механизм `docs/implementation/VDS-DEPLOYMENT.md`; не отключай контроль SSH host key, проверку CI/SHA, TLS, ACL, резервные копии и защиту восстановления.
- Не записывай секреты, токены, содержимое production-БД, приватные сообщения и персональные данные в Git, PR, публичные CI-логи и ответы.
- Разрушительные действия, сброс volumes, удаление данных, необратимые миграции, изменения ролей/доступа и потенциально несовместимые изменения схемы требуют отдельного явного согласования с владельцем и плана безопасного восстановления.
- Не создавай фальшивую активность, аккаунты или контент в production для демонстрации или проверок.
- Не утверждай, что сайт полностью готов к открытому запуску, пока не закрыты внешние правовые, модерационные и почтовые условия из `docs/implementation/STATUS.md`.

## Стиль работы

Действуй самостоятельно в пределах уже утверждённой задачи, избегай ненужных перестроек и длинных объяснений. Точные факты и подтверждённый результат важнее количества изменений. При ошибке CI выясни причину, исправь её новым коммитом и повтори проверку; не обходи падающие тесты.
