# AGENTS.md — обязательные правила WrCommunity

Действует для всего репозитория и всех AI-агентов.

## Источник истины

- Единственный репозиторий: `https://github.com/lolokeksu09/WrCommunity`, целевая ветка `main`. Перед работой сверь фактический GitHub HEAD, прочитай этот файл, [точку продолжения](docs/implementation/CONTINUATION.md), относящиеся исходники и документацию.
- Прямые решения владельца и утверждённый `docs/specs/social-core-v1.md` имеют приоритет; учитывай `docs/specs/wrcommunity-v1/`. PROPOSAL сам по себе не является утверждённым требованием.
- Сохраняй React + Fastify + PostgreSQL + worker + Docker/Caddy, API-контракты, имена и приватность. Продукт использует реальные серверные данные. Старый `wild-rift-community` — другой проект; `prototypes/home/v6/index.html` остаётся исходным прототипом.

## Обязательный порядок работы

1. **План до кода.** Для крупного патча (несколько связанных сценариев, модулей или этапов) до изменений исходников сохрани в GitHub цель, согласованный объём, ограничения и чеклист этапов в `docs/superpowers/plans/`. Укажи базовый SHA и рабочую ветку; после открытия PR добавь ссылку. Утверждённый в чате объём перенеси в документ. Для небольшой правки достаточно описания задачи в PR и точки продолжения.
2. **Актуальный код и локальный сайт.** При изменении интерфейса или пользовательского сценария изучи затронутый код и запусти приложение локально из текущей рабочей версии по [README](README.md). После изменений пересобери приложение и проверь именно новую сборку: затронутые экраны, действия и состояния на мобильном и десктопном размерах. Используй изолированную тестовую БД и данные. Сопоставь интерфейс с требованиями и кодом, посмотри локальные снимки экранов. В PR/точке продолжения зафиксируй SHA сборки и наличие незакоммиченного diff, локальный URL, viewport (ширина × высота), выполненные действия, результат и пути снимков/артефактов; шаблон — [локальный отчёт](docs/implementation/LOCAL-DEVELOPMENT.md#отчёт-о-локальном-просмотре). Если запуск недоступен, зафиксируй причину и реально выполненную альтернативную проверку; чтение кода и успешная сборка не доказывают просмотр сайта. Для правок только документации проверяй факты, ссылки и команды; локальный запуск приложения не требуется.
3. **Коммиты и документация.** Работай в короткой ветке через PR. Каждый законченный логический этап сохраняй реальным коммитом в GitHub, включая обновление относящейся документации в том же PR до merge. Готовый патч считается доставленным после сохранения в GitHub и завершения требуемых проверок/публикации. Существенные настройки также меняются через PR. При GitHub API проверяй созданный tree/commit и фактический head.
4. **Проверки по риску.** Перед функциональными изменениями прочитай [TESTING-STRATEGY](docs/implementation/TESTING-STRATEGY.md) и [реестр E2E](scripts/ci/e2e-levels.json). Промежуточно выполняй целевые L1–L3, типы и сборку по затронутым областям; для исправления поведения добавь регрессию и подтверди RED → GREEN. Запускай повторно при новых изменениях, сбоях или нерешённых рисках. Полный локальный набор после каждого этапа не требуется; FULL/RELEASE обязательны по правилам ниже.
5. **Точка продолжения.** После каждого завершённого этапа и перед остановкой обновляй [CONTINUATION](docs/implementation/CONTINUATION.md) и связанный план: ветка/PR, последний сохранённый коммит, что готово, какие проверки реально прошли, ограничения, что осталось и одно следующее действие. Запись должна позволять продолжить в другом чате без восстановления переписки. При возобновлении сверяй её с GitHub/CI и продолжай с первого незавершённого пункта. Завершённые планы помечай явно. Перед merge обозначь состояние файла как снимок разработки и явно укажи связанный PR. После merge окончательный статус берётся из его описания; успешно доставленный PR не является активной задачей из-за старого чекбокса снимка. Финальный merge SHA, RELEASE и VDS можно фиксировать в описании PR со ссылкой из точки продолжения: документ не может содержать SHA собственного будущего коммита.
6. **Доставка и отчёт.** После проверенного merge дождись RELEASE точного SHA `main`, `deploy`, строгого публичного HTTPS и `vds-status`. В итоговом отчёте укажи PR, точный SHA `main`, изменения/документы, реально просмотренные экраны и действия, результаты проверок и статус VDS. Разделяй выполненное, запланированное и недоступное. Публикация подтверждается успешным релизом и совпадением активного SHA VDS.

## CI и выбор проверок

- **Draft → FAST:** типы, сборка, секреты, CI-policy и автоматический план затронутых проверок. Для нескольких файлов используй `npm run test:affected -- --files` с полным набором путей либо `--base=<полный SHA>`. План — рекомендация, не тест.
- Для изменений интерфейса дополнительно запускай `npm run check:ui`; проверка должна завершиться успешно вместе с typecheck/build и затронутыми browser-сценариями.
- Для фактического выполнения в изолированном окружении есть `npm run test:affected -- --execute --files` с полным набором путей; `--execute --base=<SHA>` сравнивает полный diff. При server/auth/ACL расширяй API/негативные проверки по стратегии. `--list`, `--dry-run` и созданный тест не доказывают успешного исполнения.
- L1: `npm run test:l1`; L2/L3: `npm run test:l2 -- <area>` / `npm run test:l3 -- <area>` в подготовленном E2E-окружении. Новые E2E регистрируй с точными именем, уровнем и существующей областью.
- **Ready → FULL:** на последнем head SHA должны завершиться именно success: `api-tests`, оба `browser-project` (desktop/mobile), `browser-tests`, `integration`, `docker-smoke`, `quality-gate`. При skipped, pending, cancelled, failure или отсутствии обязательной job merge запрещён. После нового коммита проверяется новый SHA; при merge используй expected head.
- **main → RELEASE:** повторная полная проверка, затем `deploy` (при включённом `WRC_DEPLOY_ENABLED`) и `vds-status`; `quality-gate` предназначен для PR и на `main` может быть skipped. Если релиз/деплой пропущен или неуспешен, сообщи фактический статус.
- API, desktop и mobile выполняются на независимых runners с отдельными PostgreSQL/Mailpit; агрегаторы должны подтверждать исходные jobs. Параллелизм браузеров — три worker на runner, локально один, `fullyParallel: false`. Менять его можно только после сравнительных FULL и проверки гонок; при нестабильности верни `WRC_E2E_WORKERS: '2'`, сохранив оба проекта, повторы и покрытие. Действующие ограничения и история замеров — [стратегия, §12](docs/implementation/TESTING-STRATEGY.md#12-параллелизм-и-актуальные-источники).
- **Защита main:** на 25.10.2026 GitHub подтвердил `protected: true` и активный ruleset [25793011](https://github.com/lolokeksu09/WrCommunity/settings/rules/25793011): PR, required `integration`/`docker-smoke`/`quality-gate`, запрет force push и удаления. Перед merge перепроверь фактические правила и проверки; зелёный интерфейс Merge не заменяет этот контроль.

## Безопасность и границы

- Production разворачивается только установленным механизмом [VDS-DEPLOYMENT](docs/implementation/VDS-DEPLOYMENT.md), с проверкой SSH host key, CI/SHA, TLS, ACL, резервных копий и восстановления.
- Секреты, токены, production-БД, приватные сообщения и персональные данные остаются вне Git, PR, публичных логов и ответов. Проверочные аккаунты/контент создаются только в изолированной среде, не в production.
- Разрушительные операции, удаление данных/volumes, несовместимые миграции и изменения ролей/доступа требуют отдельного явного согласования владельца и плана восстановления. Возраст ветки сам по себе не разрешает её удаление.
- Готовность к открытому запуску определяется правовыми, модерационными и внешними почтовыми условиями из [STATUS](docs/implementation/STATUS.md), а не наличием публичного HTTPS.

## Стиль работы

Действуй самостоятельно в утверждённом объёме, сохраняй результаты по этапам. При ошибке найди причину, исправь её новым коммитом и проверь затронутое поведение. Факты и завершённый результат важнее количества изменений и проверок.
